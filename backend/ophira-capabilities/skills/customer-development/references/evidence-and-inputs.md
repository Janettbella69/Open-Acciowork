# 具体客户线索与联系实验

## 输入与适用范围

- 读取用户已选择的客户类型/市场、产品事实、供货/服务能力和本次允许的联系范围。尚未选路径时先比较渠道，而不是无边界搜集名单。
- 每条线索记录公司、公开业务入口、联系人及来源；将公司与自然人记录分开，只收集本次业务所需信息。
- 用户提供的 CRM/邮件/沟通记录需要有日期、渠道、实际内容定位和参与方。没有这些信息就保留“用户陈述/待核对”，不伪造完整互动。

## 可观察的购买信号

- 品类覆盖、扩店、新品计划、公开招标等可以成为候选依据，但需核对该事件的主体、日期与适用地区；不是已表达购买意愿。
- 明确回复、合格询盘、报价请求、样品要求、采购订单各有不同含义。不能从邮件送达、打开、点击或社媒关注推断意向或成交。
- 网页原文中可定位的内容记为 `observed_fact`（仅限该页面确实显示的内容）；用户未独立验证的材料为 `user_statement`，社区讨论为 `community_signal`，匹配度和意向推测为 `inference`。
- 每个关键字段保留 URL/文件/互动原件定位、获取与发生时间，以及宿主实际生成的 Evidence/source receipt；不存在就写“未入账/待核对”。

## 去重、排序与记录

- 相同公司不同域名/门店可能属于一个账户，也可能是独立经营主体；保留合并依据，不用名字相似直接覆盖记录。
- 基于用户的硬性约束和最新信号列短名单。已联系、拒绝、退订或停止跟进记录优先影响下一步，不能每次从空白名单重发。
- 使用 `record_interaction` 只记录真实发生且有材料支持的互动；拟发送内容保存在草稿字段/产物，不能作为已发生的发送或客户回复入账。
- 发送回执证明的是对应渠道接受/发送状态，不能代替客户已阅读、已答复或成交证据。失去原件时降低可验证状态。

## 联系实验与停止条件

- 一次实验写清对象范围、产品主张来源、语言、单一请求、观察窗口与用户确认的成功条件；不可把模板默认值当用户政策。
- 回复前不推测职位、预算、合作关系；没有可靠联系方式时交付待补入口。
- 仅在实际授权后经已配置渠道发送。禁止 Skill 自行批量发信、自动扩展跟进次数或绕过停止条件。

输出可使用 [客户开发记录](../templates/account-development.md)，按账户或小批次拆分。记录真实 ID 和来源，帮助下一轮复核，不把经验写成全局记忆或授权规则。
